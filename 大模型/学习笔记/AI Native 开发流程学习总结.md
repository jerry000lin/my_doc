# AI Native 开发流程学习总结

## 一、核心认知：流程没变，人的角色变了

AI 原生开发并不是发明了一套全新的开发流程，基本仍然是：

**可行性分析 → 设计文档 → 原型设计 → 编码实现 → 测试验证。**

真正发生变化的是执行主体：大量分析、设计、编码、调试可以交给 Agent，人更多承担关键节点的**判断、确认和决策**。因此未来真正稀缺的能力，可能越来越不是“能不能写出来”，而是“该不该做、应该怎么做、结果到底对不对”。([宝玉的分享][1])

---

## 二、第一步：可行性分析——重点不是“能不能做”，而是“值不值得做”

文章把可行性分为两个层面：

* 产品价值：用户是否真的需要？是否符合产品定位？
* 技术可行性：能不能实现？实现成本是否合理？([宝玉的分享][1])

我的进一步理解是：

> **随着大模型降低实现成本，“要不要做”可能比“能不能做”更加重要。**

很多事情技术上都能实现，但如果没有先判断价值，很可能：

**大量开发 / 分析 → 消耗时间和 Token → 最后发现没有意义。**

因此以后面对稍大的任务，可以先问：

1. 为什么要做？
2. 最终服务什么决策或用户？
3. 做出来以后会改变什么？
4. 如果什么结果出现，我应该停止继续投入？

最后一点尤其重要，即 **Stop Criteria**。

否则 Agent 很容易让工作无限延伸：

> 再分析一个维度 → 再跑一个模型 → 再补几个因子 → 再做一版结果。

---

# 三、第二步：设计文档——本质是“上下文和决策的载体”

AI 开发中，设计文档的重要性反而提高了。

它主要承担两个作用：

1. **给人检查和修改方案。**
2. **在不同 Agent Session 之间传递上下文。**

确认后的文档可以直接成为后续 Agent 实现的输入，而不需要每次重新解释需求背景。([宝玉的分享][1])

但实际使用中存在一个明显问题：

> Agent 太容易生成长文档，最终文档数量越来越多，自己反而找不到信息。

所以真正需要建立的不是“多写文档”，而是**文档治理和固定范式**。

对于系统项目，可以考虑保持少数长期入口，例如：

```text
project.md      # 当前项目目标、状态、待办、阻塞
decisions.md    # 关键决策及原因
docs/           # 真正值得长期保留的设计
```

原则：

> **不是每次 Agent 工作都产生一份新文档，而是判断哪些信息值得进入长期记忆。**

这一点对当前橙 e 贷这种长期、碎片化的数据分析项目尤其重要。

---

# 四、第三步：原型——不是把事情做两遍，而是低成本暴露错误

文章强调高精度原型，因为原型阶段修改界面、流程和交互成本很低，一旦真正实现，再修改代码、状态、测试等成本会明显增加。([宝玉的分享][1])

所以原型的价值可以理解为：

> **用很便宜的方法提前发现错误。**

只要满足：

**原型成本 < 实现之后返工成本**

就值得做。

它不只适用于 UI。

对于数据分析和模型，可以把“原型”理解成 **Cheap Prototype / Cheap Falsification**：

例如：

```text
一个月数据
→ 少量字段
→ 简单 SQL
→ 简单交叉分析
→ 看有没有信号
```

建模也可以：

```text
规则 baseline
→ Logistic Regression
→ LightGBM baseline
→ 再决定是否进行复杂特征工程
```

核心思想：

> **先用最低成本尝试证明这个方向“不值得继续”。**

如果简单方法都能看到明显价值，再增加投入。

---

# 五、第四步：实现——编码已经越来越不是主要瓶颈

当需求、设计、原型已经确认以后，Agent 可以承担大量实现工作，包括：

* 拆解任务；
* 编写代码；
* 运行测试；
* 调试错误；
* 自行验证结果。

文章强调让 Agent 建立自己的反馈循环，例如写完代码后自行运行测试、发现问题后继续修复，而不是每完成一点都让人介入。([宝玉的分享][1])

因此真正的瓶颈开始从“写代码”向两侧移动：

```text
左侧：
需求 / 判断 / 设计

        ↓

      编码

        ↓

右侧：
测试 / 验证 / 部署
```

人的精力应该逐渐更多投入左右两侧，而不是不断优化“怎么让 Agent 写代码”。

---

# 六、Agent 自测 ≠ 最终正确

Agent 的测试主要能证明：

> **代码按照它理解的问题能够运行。**

也就是：

**Implementation Correctness**

但这不代表：

> **它解决了正确的问题。**

即：

**Problem Correctness**

因此测试至少应该有两层：

### Agent 自验证

检查：

* 代码能不能运行；
* 单元测试；
* 类型错误；
* 接口；
* 边界条件；
* 基础结果。

### 人最终验证

检查：

* 功能是不是真的符合需求；
* 用户是否真的会这样使用；
* 有没有遗漏真实使用场景；
* 最终结果是否有价值。

文章因此强调，即使 Agent 已完成测试，人仍应站在普通用户视角做黑盒验证。([宝玉的分享][1])

# 七、数据分析 / 建模的“用户验证”应该怎么做

这部分与软件开发最大的区别是：

软件开发时，开发者比较容易模拟最终用户。

但数据分析通常存在：

```text
分析人员
→ 专业同事
→ 业务负责人
→ 管理层
→ 最终业务决策
```

因此分析人员不一定能够独自判断最终结果是否真正有价值。

可以把验证拆成三层。

### 第一层：技术正确性

自己 + Agent 可以负责：

* 数据重复；
* Join 膨胀；
* 空值；
* 时间穿越；
* 标签泄漏；
* 样本定义；
* 指标计算；
* 代码复现。

### 第二层：分析正确性

分析人员需要判断：

* 是否优于 baseline；
* 跨时间是否稳定；
* 不同客群是否稳定；
* 是否符合业务常识；
* 是否存在选择偏差；
* 换口径以后结论是否成立。

### 第三层：决策有效性

必须和真正的决策者确认：

> **如果这个结论成立，你准备做什么？**

例如：

> 如果证明 R1 + 高两信分客户转化显著更高，是否会改变下一轮投放策略？

如果答案是：

> “不会采取任何行动。”

那么这个分析继续深入的价值可能就很低。

真正完整的分析闭环应该是：

```text
分析
→ 判断
→ 决策
→ 行动
→ 结果反馈
```

# 八、适合数据分析 / 建模工作的 AI Native 流程

可以把文章的方法迁移成下面这套流程：

```text
1. 决策定义
   为什么做？
   谁需要这个结果？
   哪种结果会改变行动？

        ↓

2. 可行性判断
   数据是否存在？
   样本是否足够？
   指标能否定义？
   这个问题真的能靠分析 / 模型解决吗？

        ↓

3. 分析设计
   样本
   标签
   口径
   Baseline
   方法
   评价指标
   Stop Criteria

        ↓

4. Cheap Prototype
   小样本
   少量字段
   简单 SQL
   简单模型
   先判断有没有信号

        ↓

5. 正式执行
   Agent 完成 SQL、数据加工、模型、图表

        ↓

6. Agent 自验证
   行数
   唯一性
   Join
   空值
   时间
   泄漏
   指标

        ↓

7. 人工分析验证
   Baseline
   稳定性
   合理性
   敏感性
   反例

        ↓

8. 决策者确认
   结果意味着什么？
   下一步采取什么行动？
```

这本质上仍然是：

**可行性 → 设计 → 原型 → 实现 → 测试**

只是从“软件产品”迁移成了“分析决策产品”。

# 九、关于 Skills

文章提出一个比较值得记住的观点：

**大部分纯 Coding Skills 未必有很高价值。**

因为当前模型的编码能力已经较强，真正值得增强的反而是：

* 左侧：设计、原型、需求确认；
* 右侧：测试、自动部署、自动发布、自动执行。([宝玉的分享][1])

因此与其花大量时间研究：

> “如何让 Agent 更会写代码？”

不如研究：

> **如何让 Agent 得到正确的问题、正确的上下文和明确的验证标准。**

---

# 十、这篇文章对我的最大启发

最终可以浓缩成一句：

> **AI 越擅长执行，人越需要擅长判断。**

以后真正值得训练的能力包括：

**定义问题。**

**判断值不值得做。**

**设计最低成本的验证方法。**

**判断什么时候应该停止。**

**验证 Agent 是否解决了真正的问题。**

**把分析结果连接到真实决策。**

这恰好也是目前橙 e 贷工作让我感到困难的地方。

过去熟悉的是：

> 不会 → 学习 → 实现 → 解决。

现在逐渐进入：

> **问题是否值得解决？**

> **真正的问题是什么？**

> **这个结果意味着什么？**

> **应该采取什么行动？**

这不是简单的编码能力升级，而是在从**执行者**逐渐向**问题定义者和决策支持者**转变。
