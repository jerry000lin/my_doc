下面这 10 个答案可以直接作为你的**基础概念标准答案**。

# 1. Model 和 Agent 有什么区别？

**Model 是负责推理和生成的模型；Agent 是围绕 Model 建立的一套执行系统。**

Model 能做的是：

* 接收 Messages；
* 生成文字；
* 生成结构化结果；
* 判断是否需要调用工具；
* 生成工具名称和参数。

Agent 通常包含：

```text
Model
+ System Prompt
+ Tools
+ 工具调用循环
+ State
+ Middleware
```

所以：

```text
Model：做一次判断和生成
Agent：反复调用模型和工具，直到完成任务
```

LangChain 官方将 Agent 概括为 **Model + Harness**；Harness 就是模型外面的提示词、工具、循环和中间件等执行机制。([LangChain 文档][1])

**记忆：模型负责思考，Agent 负责把事情做完。**

---

# 2. Tool 到底是谁执行的？

**Tool 是由你的 Python 程序，也就是 LangChain/LangGraph 运行时执行的，不是模型执行的。**

完整过程是：

```text
模型输出：
调用 execute_sql，
参数 query="SELECT ..."

        ↓

LangChain 读取 tool_call

        ↓

Python 真正调用 execute_sql(...)

        ↓

执行结果封装为 ToolMessage

        ↓

再次交给模型
```

模型只负责决定：

```text
调用哪个 Tool
传入什么参数
```

程序负责：

```text
查数据库
访问 API
读写文件
发送邮件
执行代码
```

官方文档将 Tool 定义为具有明确输入和输出的可调用函数；模型决定何时调用和使用哪些参数，运行时负责实际调用。([LangChain 文档][2])

**记忆：模型提议调用，程序真正执行。**

# 3. AIMessage 和 ToolMessage 是什么关系？

**AIMessage 表示模型的输出；ToolMessage 表示某次工具调用的执行结果。**

典型消息顺序是：

```text
HumanMessage
    用户问题
        ↓
AIMessage
    模型提出 tool_call
        ↓
ToolMessage
    程序返回工具结果
        ↓
AIMessage
    模型根据工具结果生成最终答案
```

例如：

```text
AIMessage:
调用 execute_sql
tool_call_id = "call_123"

ToolMessage:
查询结果为 18.86
tool_call_id = "call_123"
```

`tool_call_id` 用来说明：

> 这个 ToolMessage 是对哪一个工具调用的回答。

因此，一个 AIMessage 可以包含多个 `tool_calls`，随后也可能出现多个对应的 ToolMessage。Messages 是模型上下文的基本单位，ToolMessage 专门承载工具执行结果。([LangChain 文档][3])

**记忆：AIMessage 提出调用，ToolMessage 返回结果。**

# 4. Runtime Context 和 State 有什么区别？

## Runtime Context

保存本次调用需要使用的、相对稳定的外部依赖或配置，例如：

```text
数据库连接
当前用户 ID
用户权限
文件存储器
配置对象
脚本执行器
```

例如：

```python
@dataclass
class RuntimeContext:
    db: SQLDatabase
    user_id: str
```

## State

保存执行过程中不断变化的数据，例如：

```text
messages
已经生成的 SQL
SQL 查询结果
错误信息
重试次数
当前任务状态
```

例如：

```python
class AgentState(TypedDict):
    messages: list
    sql: str | None
    result: str | None
    retry_count: int
```

两者的核心区别：

```text
Context：运行依赖，通常不会随着流程不断变化
State：流程数据，会被节点不断读取和更新
```

官方将 Runtime Context 描述为一次 Agent 调用中的静态信息，例如用户 ID、数据库连接和其他依赖；State 则是执行过程中变化的动态数据。([LangChain 文档][4])

**记忆：Context 放依赖，State 放过程。**

# 5. Middleware 用来做什么？

**Middleware 用来介入并控制 Agent 的执行过程，处理多个步骤都会涉及的横切逻辑。**

常见用途：

```text
动态修改 System Prompt
记录模型调用日志
记录工具调用日志
权限检查
工具审批
重试与降级
模型动态选择
调用次数限制
限流
敏感信息检查
上下文压缩
```

Middleware 可以在这些位置介入：

```text
Agent 开始前
模型调用前
模型调用外层
模型响应后
工具调用外层
Agent 结束后
```

例如：

```text
业务功能：执行 SQL 查询
Middleware：
    查询前检查权限
    记录执行耗时
    失败后重试
    危险 SQL 要求审批
```

Middleware 不是业务流程中的普通节点，而是围绕 Agent 生命周期执行的控制机制。官方将其用于日志、Prompt 转换、工具控制、重试、限流和 Guardrail 等。([LangChain 文档][5])

**记忆：Agent 负责业务，Middleware 管 Agent 怎么执行。**

# 6. LangGraph 的三个基本元素是什么？

```text
State + Node + Edge
```

## State

图中所有节点共享和更新的数据。

## Node

一个具体处理步骤，例如：

```text
调用模型
生成 SQL
执行 SQL
检查结果
生成回答
```

## Edge

决定节点之间的执行顺序：

```text
Node A → Node B
```

也可以进行条件路由：

```text
执行 SQL
  ├── 成功 → 生成回答
  └── 失败 → 重新生成 SQL
```

**记忆：State 保存数据，Node 处理数据，Edge 决定下一步。**

LangGraph 的 Graph API 使用 StateGraph 描述由状态、节点和边组成的执行图。([LangChain 文档][6])

# 7. Node 应该返回什么？

**Node 应该返回对 State 的部分更新，而不是返回完整 State，也不应该直接修改传入的 State。**

例如当前状态：

```python
{
    "question": "查询销售额",
    "sql": None,
    "result": None,
}
```

生成 SQL 的节点只需返回：

```python
def generate_sql(state):
    sql = "SELECT ..."
    return {"sql": sql}
```

不需要返回：

```python
return {
    "question": state["question"],
    "sql": sql,
    "result": state["result"],
}
```

LangGraph 会把：

```python
{"sql": sql}
```

合并进原有 State。

特殊情况下，节点也可以返回 `Command`：

```python
return Command(
    update={"retry_count": 1},
    goto="generate_sql",
)
```

这表示同时：

```text
更新 State
+
决定下一步节点
```

官方建议节点直接返回 State 更新，不要原地修改 State；节点不需要返回完整状态。([LangChain 文档][7])

**记忆：Node 读取完整 State，只返回自己修改的部分。**

# 8. Reducer 为什么存在？

**Reducer 用来决定 State 中某个字段收到新值时，应该覆盖旧值，还是与旧值合并。**

默认情况下通常是覆盖：

```text
旧值：retry_count = 1
新值：retry_count = 2

结果：retry_count = 2
```

但是列表可能需要追加：

```text
旧值：["消息1"]
新值：["消息2"]

期望结果：
["消息1", "消息2"]
```

因此可以定义 Reducer：

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]
```

含义是：

```text
节点返回的新消息
不是直接覆盖旧消息，
而是通过 add_messages 进行合并。
```

Reducer 在并行节点同时更新同一个字段时尤其重要，否则 LangGraph 不知道这些更新应该如何组合。每个 State 字段都可以有独立的 Reducer；如果未指定，默认更新会覆盖旧值。([LangChain 文档][6])

**记忆：Reducer 是 State 字段的更新规则。**

# 9. Interrupt 和 Checkpointer 有什么关系？

**Interrupt 负责暂停执行，Checkpointer 负责保存暂停时的状态，使流程之后能够恢复。**

流程是：

```text
节点运行
   ↓
调用 interrupt()
   ↓
暂停图执行
   ↓
Checkpointer 保存当前 State
   ↓
等待人工输入
   ↓
使用 Command(resume=...) 恢复
   ↓
根据 thread_id 找到之前的状态
   ↓
继续运行
```

例如：

```python
approved = interrupt({
    "question": "是否批准执行 SQL？",
    "sql": sql,
})
```

恢复：

```python
graph.invoke(
    Command(resume=True),
    config=config,
)
```

没有 Checkpointer，Interrupt 无法可靠地跨请求保存位置并恢复；还需要使用相同的 `thread_id` 找到原来的执行线程。([LangChain 文档][8])

需要特别注意：

> 恢复 Interrupt 时，所在 Node 通常会从头重新执行，而不是从 `interrupt()` 的下一行物理续跑。

因此，写在 `interrupt()` 之前的数据库写入、发邮件等副作用操作，应当保证幂等，或者移动到审批之后。([LangChain 文档][8])

**记忆：Interrupt 按暂停键，Checkpointer 保存进度。**

# 10. Checkpointer 和 Store 有什么区别？

## Checkpointer

保存某个 `thread_id` 对应的图执行状态快照。

主要用途：

```text
短期记忆
多轮对话
Interrupt 恢复
故障恢复
状态历史
Time Travel
```

它关注的是：

> 这个执行线程现在运行到了哪里？

例如：

```text
thread_id = conversation_001
```

对应保存：

```text
当前 messages
执行到哪个节点
当前 State
下一步节点
历史 Checkpoint
```

## Store

保存跨 Thread 使用的长期数据。

主要用途：

```text
用户偏好
用户画像
长期知识
跨会话记忆
业务经验
```

例如同一个用户有三个会话：

```text
thread_001
thread_002
thread_003
```

Checkpointer 分别保存三个会话的状态；Store 可以让三个会话共同读取：

```text
用户喜欢中文回答
用户所在部门
用户常用的数据表
长期保存的业务规则
```

官方说明，Checkpointer 按 Thread 保存图状态快照；而 Store 用于保存需要跨 Thread 共享的信息。([LangChain 文档][9])

**记忆：Checkpointer 保存一次流程，Store 保存长期信息。**

# 最终速记版

```text
1. Model 负责推理，Agent 负责完成任务。
2. 模型提出 Tool Call，Python 程序执行 Tool。
3. AIMessage 提出调用，ToolMessage 返回结果。
4. Context 放运行依赖，State 放变化数据。
5. Middleware 控制和扩展 Agent 的执行过程。
6. LangGraph = State + Node + Edge。
7. Node 读取 State，返回部分 State 更新。
8. Reducer 决定新旧状态如何合并。
9. Interrupt 负责暂停，Checkpointer 负责保存和恢复。
10. Checkpointer 保存当前 Thread，Store 保存跨 Thread 长期数据。
```

其中最核心的一条主线是：

```text
LangChain Agent：
Model → Tool Call → ToolMessage → Model

LangGraph：
State → Node → Edge → 下一个 Node
```
